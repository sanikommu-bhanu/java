Output equals the expected output. Without passing the IOException into the constructor, getCause() is null and e.getCause().getMessage() throws NullPointerException (shown in the extra demo).
Hierarchy: ExamException <- ExamClosedException, NotRegisteredException, FileTooLargeException, SubmissionStorageException (all checked: the caller can recover and must decide). Propagation: Storage (IOException wrapped) -> Service -> Controller, which translates it into a student-friendly message; the full chain is kept for the log.
JOINT: a meaningful SubmissionStorageException hides storage details from the UI, lets the controller react per type and keeps the original IOException as the cause.
ALTERNATIVE (unchecked): no 'throws' clauses or forced try/catch, easier to forget handling; stack trace capture costs O(depth) time and space per exception either way; chaining keeps the cause object (and its trace) alive as long as the outer exception.
